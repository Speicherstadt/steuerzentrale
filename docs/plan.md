# Projektplan

Die Steuerzentrale installiert, aktualisiert, sichert und überwacht die Apps der Speicherstadt auf
Servern: auf gemeinsamen Servern, auf einem eigenen Server je Kunde oder auf einem Server beim
Kunden. Sie ist das Werkzeug für Hosting, Wartung und Support, Open Source unter der AGPL. Was
gebaut wird und in welcher Reihenfolge, steht in der
[Bauliste](https://github.com/Speicherstadt/steuerzentrale/blob/main/BAULISTE.md).

## Ziel

- **Ein Ort für alle Server und Installationen**: welcher Kunde welche App auf welchem Server hat, in
  welcher Version, ob sie gesund ist und wann das letzte Backup lief.
- **Updates ohne Handarbeit**: neue Versionen in Wellen, mit Backup vorher, Prüfung danach und
  Rückkehr zur alten Version, wenn die Prüfung fehlschlägt; nie in einer Sperrzeit einer App.
- **Server pflegen**: Betriebssystem-Updates, Neustarts im Wartungsfenster, Platte, Zertifikate,
  Backups, offene Ports, Mail-Zustellbarkeit.
- **Support mit Spur**: Zugriff auf eine Installation nur zeitlich begrenzt, mit Grund, protokolliert
  und für den Kunden sichtbar.
- **Keine App ist fest eingebaut**: Jede App beschreibt sich in einem Manifest; die Steuerzentrale
  kennt nur das Manifest.

**Bewusst nicht in der Steuerzentrale**: Buchung, Bezahlung, Rechnungen, Tickets und alles, was der
Kunde selbst sieht (das Portal, ein eigenes Projekt); Server bei Anbietern bestellen (später, über
deren API); Fernwartung von Geräten beim Kunden (Kontext-Box, Stellwerk-Agenten, Desktop-Apps).

## Aufbau

```text
                 Portal (eigenes Repo, öffentlich)
                        │  api.<domain>: Kunden, Buchen, Kündigen, Lesen; Webhooks zurück
                        ▼
  Betrieb ──VPN──▶  Zentrale  ◀── agent.<domain>: WSS, Client-Zertifikat je Server
                        │   └── DNS-API (Cloudflare): A, AAAA, Prüfung der Kundendomains
       ┌────────────────┼────────────────┐
   Server A          Server B          Server C (beim Kunden,
   Agent             Agent             Portweiterleitung 80/443)
   Pforte (Caddy)    Kontext allein    Agent, Pforte
   Haben, Soll, …    (rootful)         Belegt, Kennwort
```

- **Zentrale**: Server mit API und Oberfläche; läuft genau einmal. Drei Hostnamen: die Oberfläche
  nur über VPN, `agent.<domain>` für die Agenten und `api.<domain>` für das Portal öffentlich.
- **Agent**: kleines Programm auf **jedem** verwalteten Server, als systemd-Dienst. Er baut die
  Verbindung selbst auf (kein offener Port für ihn), meldet Heartbeat, Fakten und Zustand und führt
  Aufträge aus. Er führt nur Aktionen aus signierten Manifesten aus; eine freie Shell gibt es nicht.
  Backups laufen als systemd-Timer auf dem Server weiter, auch wenn die Zentrale ausfällt.
- **Pforte**: ein Caddy je Server unter dem Nutzer `sz-pforte`. Er nimmt 80 und 443 an, holt die
  Zertifikate (HTTP-01) und leitet jede Adresse an den lokalen Port ihrer Installation.
- **Ein-Server-Betrieb**: Zentrale und Agent auf derselben Maschine, für Selbsthoster.
- **Portal**: öffentliche Website mit Buchung, Bezahlung und Kundenbereich, ein eigenes Repo. Es
  spricht nur über `api.<domain>` mit der Zentrale und bekommt Ereignisse per Webhook.

### Ablauf: Server hinzufügen

1. In der Zentrale „Server hinzufügen“: Name, Art (gemeinsam, eigen, beim Kunden), Wartungsfenster.
2. Die Zentrale zeigt einen Befehl mit Einmal-Token (24 h):
   `curl -fsSL https://agent.<domain>/install.sh | sudo sh -s -- --token …`
3. Das Skript prüft Debian 13 oder Ubuntu 24.04 (amd64, arm64; Podman ab 4.9), cgroup-v2-Delegation und Uhrzeit, installiert Podman, minisign, unattended-upgrades und den
   Agenten (Prüfsumme und Signatur), erlaubt rootless Ports ab 80 und hinterlegt den öffentlichen
   Schlüssel für Manifeste. Der Agent tauscht das Token gegen sein Client-Zertifikat.
4. Der Server erscheint mit seinen Fakten: CPU, RAM, Platte, Architektur, IPv4, IPv6, PTR, Ports,
   ausgehender Port 25.

### Ablauf: App installieren

1. Kunde, App, Server, Optionen wählen. Die **Platzierung** (reine Funktion) prüft Manifest, Server
   und vorhandene Installationen und liefert „passt“, Hinweise oder Gründe.
2. Einstellungen nach Ebenen: Betreiber (einmal), Installation (je Kunde), automatisch (Secrets).
3. Die Zentrale vergibt den lokalen Port, rendert die Quadlet-Units und Podman-Secrets, setzt den
   DNS-Eintrag und schickt den Auftrag. Bietet eine andere Installation des Kunden einen
   Anmeldedienst, legt ein vorgeschalteter Auftrag dort den OIDC-Client an.
4. Der Agent legt den Linux-Nutzer `sz-<installation>` an, schreibt Units und Secrets, zieht die
   Images per Digest, führt die Einrichtungsschritte aus, startet und trägt die Adresse in die Pforte
   ein. Fertig ist die Installation, wenn Health innen und die Prüfung von außen grün sind.

### Ablauf: Update

1. Eine neue Version erscheint in der Registry mit signiertem Manifest.
2. Die Zentrale plant Wellen: in Stufe 1 „intern“ und „alle“, ab Stufe 2 intern → früh (SLA Plus) →
   standard (Basis) → spät (Ruhe); jede erst nach 24 h ohne Störung, nie in einer Sperrzeit; ab
   Stufe 2 bekommt jeder Kunde den Termin 72 h vorher (Webhook an das Portal). Ein als **dringend** markiertes Update (Sicherheitslücke,
   Mindestversion von ERiC) läuft sofort durch alle Wellen; eine Sperrzeit übergeht nur der Inhaber
   mit Grund.
3. Je Installation: Backup, Image ziehen, Schritte nach dem Update, Neustart, Health; bei Rot zurück
   auf die alte Version und das Backup, Welle anhalten, Meldung.

Eine **Störung** ist: Health innen oder außen länger als 5 Minuten rot, oder eine Rückkehr nach einem
Update.

geprüft (`scripts/manifeste.test.ts`); „noch nicht“ heißt: für die Version des Manifests gibt es kein
veröffentlichtes Image.

## Manifest

Eine YAML-Datei je App und Version (`manifeste/<app>/<version>/manifest.yml`), geprüft mit dem Zod-Schema aus `packages/manifest`, als JSON
Schema veröffentlicht und mit dem Signierschlüssel des Betreibers signiert. Beispiel, gekürzt:

```yaml
schema: 1
id: haben
version: 1.9.0
lizenz: AGPL-3.0-only
quelle: https://github.com/Speicherstadt/haben
container:                       # daraus werden Quadlet-Units (Vorbild: deploy/quadlet/)
  - { name: app, image: docker.io/tristanteu/haben@sha256:…, braucht: [db], env: [ELSTER_HERSTELLER_ID],
      volumes: [{ name: belege, pfad: /app/belege }] }
  - { name: db, image: docker.io/tristanteu/haben-db@sha256:…, volumes: [{ name: daten, pfad: /var/lib/postgresql/data }] }
architektur: [amd64, arm64]      # je Container übersteuerbar, z. B. Schreibzeug nur amd64
ressourcen: { ram_mb: 2048, platte_gb: 10 }   # RAM als Grenze (MemoryMax), Platte als Planwert
netz:
  http: { dienst: app, port: 3000, websocket: false, sse: false, max_body_mb: 100, timeout_s: 60 }
  ports: []                      # Kontext: [{ dienst: stalwart, port: 25, fest: true }], Stellwerk: [{ dienst: zentrale, port: 22001, fest: false }]
  oeffentliche_ipv4: false
  mail: false                    # true: PTR, Port 25 ausgehend, Blacklist-Prüfung
  server_fuer_sich: false
proxy: geteilt                   # eigen: App bringt Caddy mit, nur mit server_fuer_sich
rootful: false                   # true nur mit server_fuer_sich
optionen: []                     # schalten Container zu, mit eigener Architektur und RAM
braucht: []                      # Kennwort: [oidc-anbieter]
bietet: []                       # Kontext: [oidc-anbieter, smtp]
anmeldung: oidc                  # oidc | eigen | anbieter
health: { art: keine, hinweis: Haben#946 }    # http | tcp | befehl | keine
befehle: {}                      # benannte Befehle: { name: { container, argv: [...] } }
schritte: { einrichten: [], nach_update: [] } # nur Namen aus befehle
backup:
  - { art: pg_dump, container: db, datenbank: haben, nutzer: haben }
  - { art: volume, volume: belege }
aktionen: { nur_lesen: nicht_unterstuetzt, export: nicht_unterstuetzt }
sperrzeiten: [{ monatlich: "07-12", grund: Umsatzsteuer-Voranmeldung }]
dns: []                          # Kontext: MX, SPF, DKIM, DMARC, autoconfig
env:
  - { name: ELSTER_HERSTELLER_ID, ebene: betreiber, pflicht: true }
  - { name: LAYOUTS_MAX_COUNT, ebene: installation, typ: zahl, vorgabe: 20 }
  - { name: BETTER_AUTH_SECRET, ebene: auto, erzeugen: zufall_32 }
  - { name: OIDC_CLIENT_SECRET, ebene: auto, aus: oidc-anbieter }
hinweis: Haben ist Open Source (AGPL), https://haben.app
```

| Ebene | Wer setzt sie | Beispiel |
| --- | --- | --- |
| `betreiber` | der Betreiber, einmal je App | Hersteller-ID für ELSTER, API-Schlüssel für KI |
| `installation` | der Betreiber je Installation, mit Vorgabe | Grenzen, Domain für Mail |
| `auto` | die Zentrale, nie von Hand | Secrets, URL, OIDC-Client vom Anbieter des Kunden |

## Entscheidungen

Der Loop entscheidet danach und trägt neue Entscheidungen hier mit Grund ein.

| Frage | Entscheidung | Warum |
| --- | --- | --- |
| Wo die Zentrale läuft | genau einmal, auf einem eigenen Server (netcup); im Ein-Server-Betrieb neben dem Agenten. Oberfläche nur über WireGuard; `agent.<domain>` und `api.<domain>` öffentlich, nur mit Client-Zertifikat bzw. Token und Rate-Limit | Server beim Kunden haben wechselnde IPs; install.sh muss erreichbar sein; die Oberfläche bleibt privat |
| Wer die Verbindung aufbaut | immer der Agent, ausgehend per WSS mit Client-Zertifikat je Server (mTLS), rotierbar, sofort sperrbar | kein offener Port für den Agenten; ein Zertifikat gilt nur für einen Server |
| Was der Agent ausführt | nur Manifeste mit gültiger Signatur des Betreibers; der öffentliche Schlüssel wird bei der Installation hinterlegt, der private liegt offline beim Inhaber, nie auf der Zentrale. Images nur per Digest; Schritte nur als benannte Befehle mit argv, nie als Shell-Text | eine übernommene Zentrale darf keinen Code auf den Servern ausführen können |
| Protokoll und Versionen | jede Nachricht trägt `typ` und die Protokollversion ihres Absenders; Versionen fügen nur hinzu; die Zentrale liest die eigene und die vorige Version und wertet eine ältere Nachricht schrittweise auf (`AUFWERTUNGEN`); der Agent liest nur die Version seiner Zentrale; je Version liegt ein eingefrorenes Beispiel jeder Nachricht im Code, das spätere Versionen weiter lesen müssen; eine Nachricht hat höchstens 4 MiB (`MAX_NACHRICHT_BYTES`), größere werden weder gesendet noch gelesen | ein Agent ist nach einem Update der Zentrale bis zu seinem eigenen Update eine Version zurück (Z-504); ohne Grenze könnte ein Feld (Logzeile, Fehlertext, Daten) Speicher und Datenbank der Gegenseite füllen |
| Aufträge | in der Zentrale gespeichert, idempotent mit ID; der Agent holt, bestätigt, meldet; Aufträge können aufeinander warten, auch über Installationen hinweg | Netze brechen ab; der OIDC-Client entsteht beim Anbieter, bevor die App startet |
| Warteschlange der Aufträge | Tabelle `auftraege` je Betreiber: Server, Installation, Aktion (Name eines Befehls unter `befehle`), Argumente (JSON), Zeitlimit, Zustand, `wartet_auf` (JSON-Liste von Auftrags-IDs desselben Betreibers, auf jedem Server), Fortschritt, Ergebnis; der Auftrag trägt Text und Signatur des Manifests selbst, seit Z-501 aus `manifeste` (bzw. der Installation), dazu App, Version und SHA-256; das Audit-Log vermerkt Text und Signatur nur als „[ausgelassen]“; Zustände und Übergänge als reine Funktion in `packages/protokoll` (`uebergang`), ein ungültiger Übergang ist ein Fehler als Wert, eine doppelte Meldung ändert nichts; endet ein Auftrag, werden seine wartenden Nachfolger in derselben Transaktion bereit oder abgebrochen (ein abgebrochener gibt das weiter); die Zentrale schickt einem Agenten nach `willkommen` alle bereiten und bei ihm liegenden Aufträge und einen Auftrag, sobald er bereit wird; ein Zyklus und ein Vorgänger eines anderen Betreibers werden abgelehnt; die Zentrale prüft Aktion und Argumente schon beim Anlegen gegen das Manifest, die Signatur prüft nur der Agent | ein falscher Auftrag soll nicht erst nach seinen Vorgängern scheitern; der Text im Audit-Log wäre bei jedem Auftrag dieselben Kilobytes; ohne Manifest-Tabelle braucht der Agent die Bytes trotzdem |
| Nachrichten der Aufträge | Zentrale → Agent `auftrag`, Agent → Zentrale `bestaetigt`, `fortschritt`, `ergebnis` (die Namen aus Z-301 bleiben); noch zu Protokoll 1 kommen die Grenzen `schritt` ≤ 200 und `fehler` ≤ 2000 Zeichen; ein Agent meldet nur Aufträge seines eigenen Servers, eine Meldung zu einem anderen protokolliert die Zentrale und verwirft sie, ohne die Verbindung zu beenden | Protokoll 1 ist noch nicht veröffentlicht („Nachrichten vor dem ersten Release“); eine abgelehnte Meldung ist kein kaputtes Protokoll |
| Fortschritt eines Auftrags | der erste Fortschritt setzt den Zustand `laeuft` über `schreiben`; jeder weitere ist ein Messwert (`fortschrittSetzen` in `modules/audit/messwerte.ts`, nur die Spalten `fortschritt` und `fortschritt_am`, nur solange der Auftrag läuft), höchstens einer alle 5 Sekunden je Auftrag und Verbindung | Schritte sind Anzeige, keine Handlung; ein Agent, der sie im Takt schickt, soll das Audit-Log nicht füllen |
| Was ein Auftrag ausführt | nur einen Befehl unter `befehle` eines Manifests mit gültiger Signatur, mit `podman exec <installation>-<container> argv…` (der Containername der Quadlet-Unit), als festes argv ohne Shell, ohne Eingabe, Ausgabe verworfen; der Name der Installation folgt derselben Regel wie in den Units; Neustart, Log-Auszug, Installieren und Update sind keine Befehle und kommen mit ihren Punkten; unter dem Linux-Nutzer der Installation läuft der Befehl ab Z-402 | `befehle` ist die einzige Aktionsart im Schema mit argv; ein Name der Installation, der mit `-` beginnt, könnte sonst als Option von podman gelesen werden |
| Argumente eines Befehls | der Befehl erklärt sie unter `argumente` (`text` mit Pflicht-`muster`, `zahl`, `ja_nein`, `auswahl`); jedes erklärte ist Pflicht, ein unbekanntes wird abgelehnt; ein Wert ersetzt `${arg:<name>}` als ganzes argv-Element, nie als Programm; Zentrale und Agent prüfen mit derselben Funktion (`befehlFuellen`) | ohne Schema wäre jedes Argument ein Umweg um die Signatur; ein optionales Argument bräuchte Regeln für ein fehlendes Element, die noch kein Befehl braucht |
| Zeitlimit eines Auftrags | `zeitlimit_s` des Befehls, sonst 900 Sekunden (wie `TimeoutStartSec` der Units), höchstens ein Tag; der Agent nimmt das Kleinere aus Manifest und Auftrag, beendet den Befehl danach mit SIGKILL und meldet „Zeitlimit … überschritten“; der Befehl läuft in einer eigenen Sitzung, SIGKILL geht an die ganze Prozessgruppe (`runuser`, `env`, `podman exec`), und jeder Lauf trägt im Container die Marke `STEUERZENTRALE_LAUF=<uuid>` (`podman exec --env`), an der der Agent nach dem Zeitlimit den Befehl unter conmon findet und beendet | die Zentrale ist nicht signiert und darf eine Frist nur kürzen; ein Befehl ohne Frist könnte den Auftrag für immer laufen lassen; `runuser` forkt, und conmon startet den Befehl in einer eigenen Prozessgruppe, die mit `podman exec` nicht endet (Podman 4.9 hat dafür keine Option): ohne beides sammelten sich verwaiste Prozesse an, bei einer Health-Prüfung alle 30 s |
| Gedächtnis des Agenten | `/var/lib/steuerzentrale/auftraege.json` (0600, atomar geschrieben, ein Schreiben nach dem anderen): „läuft“ vor dem Start, „fertig“ mit Ergebnis vor dem Senden; ein Auftrag, den der Agent kennt, wird nie ein zweites Mal ausgeführt, er schickt das gespeicherte Ergebnis oder, solange er läuft, nur `bestaetigt`; erledigte Einträge nach 30 Tagen vergessen; eine unlesbare Datei heißt: keine Aufträge, bis sie repariert ist | doppelt zugestellt muss einmal ausgeführt heißen; ohne das Gedächtnis könnte der Agent das nicht mehr erkennen |
| Aufträge nach einem Neustart des Agenten | ein Auftrag, der als „läuft“ in der Datei steht, ohne im Prozess zu laufen, wird beim nächsten Zustellen als gescheitert gemeldet („Agent neu gestartet“); nur ein Befehl mit `idempotent: true` im Manifest wird stattdessen noch einmal ausgeführt; die Zentrale stellt ihn nach dem Neustart ohnehin wieder zu | ein halb gelaufener Befehl (Migration, Wiederherstellung) darf nicht blind wiederholt werden; ob er das verträgt, weiß nur das signierte Manifest |
| Log-Auszüge der Aufträge | bleiben in `log_auszuege` (mit `auftrag_id`, 30 Tage in der bestehenden Aufbewahrung); der Agent schickt sie erst ab Z-405, mit ersetzten Werten der Geheimnisse („Log-Auszug“) | eine Ausgabe mit einem Geheimnis darf nicht in die Zentrale gelangen |
| Orchestrierung | Podman-Quadlets unter systemd, rootless: je Installation ein Linux-Nutzer `sz-<installation>` mit Linger, Units in `~/.config/containers/systemd/`; `AutoUpdate` nie gesetzt; kein Docker, kein Compose | Stack-Vorgabe (`tech-stack.md`); Kunden durch Linux-Nutzer getrennt; Updates nur über die Wellen |
| Pforte | Caddy rootless unter `sz-pforte` mit `Network=host`; jede Installation hat ein eigenes `.network` und veröffentlicht ihren HTTP-Dienst nur per `PublishPort=127.0.0.1:<port>:…`, den Port vergibt die Zentrale; die Client-IP kommt im Header `X-Forwarded-For` der Pforte an; `net.ipv4.ip_unprivileged_port_start=80`; die Admin-API nur über einen Unix-Socket („Admin-API der Pforte“) | ein Caddy kann den Netzen anderer Nutzer nicht beitreten; App und Datenbank teilen das Netz ihrer Installation |
| Ressourcen | `ram_mb` ist eine Grenze (`MemoryMax`) und die Platzierung rechnet mit Überbuchung 1,0; `platte_gb` ist in Stufe 1 nur Planwert, Z-702 misst die Belegung und warnt | rootless Volumes auf ext4 kennen keine Größenquote; ein Kunde darf den RAM nicht füllen |
| Ports | feste Ports (Mail) nur einmal je Server; Ports mit `fest: false` vergibt die Zentrale je Installation | ein zweiter Stellwerk-Kunde passt auf denselben Server |
| Mehrere Kunden auf einem Server | erlaubt („gemeinsam“); eine Installation gehört genau einem Kunden | einfache Trennung, einfaches Löschen |
| Server beim Kunden | mit Portweiterleitung 80/443 (und den Ports der App) auf den Server; kein Cloudflare Tunnel in 1.0 | ein Tunnel von Cloudflare beendet TLS und sieht die Daten (Unterauftragsverarbeiter in den USA); ein eigener Relay kommt später |
| DNS | Cloudflare als DNS-Anbieter, nur DNS, kein Proxy; die Zentrale setzt A und AAAA für `<app>.<kunde>.<domain>` per API; Server bekommen nie einen DNS-Token; eigene Domains des Kunden per CNAME, aktiv erst nach Prüfung; Zertifikate per HTTP-01 an der Pforte | ein übernommener Server darf keine Kunden umleiten können; Let's Encrypt erlaubt 50 neue Zertifikate je Domain und Woche, genug für den Start |
| Mail (Kontext) | die Zentrale zeigt MX, SPF, DKIM, DMARC und PTR aus dem Manifest und prüft sie; setzt sie selbst, wenn die Domain bei uns liegt | sonst landet Mail im Spam |
| Single Sign-on | hat der Kunde Kontext, ist es sein Anmeldedienst: die Zentrale legt dort per Auftrag den OIDC-Client jeder weiteren App an; ohne Kontext nutzt jede App ihre eigene Anmeldung | ein Anbieter je Kunde, kein zusätzlicher Dienst |
| Manifest-Schema | Feldnamen deutsch wie im Plan; unbekannte Felder sind ein Fehler; Verweise (Container, Befehle, Volumes, Einstellungen) prüft eine eigene Regelstufe nach dem Zod-Schema; ein Befehl darf keine Shell starten (`sh`, `bash`, `env`, …); `pg_dump` nennt `datenbank` und `nutzer`; die Signatur wird über die exakten Bytes vor dem YAML geprüft, beide minisign-Formate (`ED`, `Ed`) | ein Tippfehler darf nicht still übergangen werden; benannte Befehle wären sonst ein Umweg zur Shell |
| Manifeste | Ablage `manifeste/<app>/<version>/manifest.yml` mit `manifest.yml.minisig`, signiert vom Inhaber; die Zentrale bekommt ein Manifest per Import (Upload oder Befehl) und zeigt eine neue Version in der Registry als „Manifest fehlt“, bis es da ist; Digests kommen aus der Registry über `scripts/digest.ts` (Quelle: Registry, Tag, abgefragt am); ein App-Repo kann später ein eigenes Manifest liefern | der Schlüssel liegt offline, also kann die Zentrale nicht selbst signieren; die App-Repos nennen nur Tags |

| Ziel der Health-Prüfung | beim Einrichten rendert der Agent aus dem signierten Manifest und den Ports des Auftrags das Ziel und merkt es sich mit den Units unter `pruefung` am Eintrag `fertig`: der Host-Port eines Dienst-Ports ist bei `netz.http` (gleicher Dienst und Port) der `httpPort`, bei einem `tcp`-Port aus `netz.ports` (auch in einem Bereich `bis`) der vergebene oder feste; `http` ohne `port` prüft den Port von `netz.http`; ein Port, der so nicht auf dem Host liegt, oder ein `befehl` mit Argumenten heißt `nicht_pruefbar` mit Grund und wird als Health `unbekannt` gemeldet; `befehl` hat höchstens 30 s, weniger, wenn sein `zeitlimit_s` kürzer ist; ein Eintrag ohne `pruefung` (vor Z-403 eingerichtet) meldet keine Units und Health `unbekannt`, bis die Installation neu eingerichtet ist | nur Ports, die auf 127.0.0.1 veröffentlicht sind, erreicht der Agent ohne `podman exec`; Kontext (`health` auf `kontext:3000` hinter dem eigenen Caddy) bleibt so `unbekannt`, nie fälschlich grün oder rot, bis sein Manifest einen veröffentlichten Port nennt; die Zentrale kann die Health einer Installation nicht auf ein anderes Ziel lenken |
| Meldung des Zustands | `zustand` geht gleich nach `willkommen` und dann alle 30 s (`ZUSTAND_MS` im Agenten) im festen Takt; läuft eine Runde noch, fällt die nächste aus; alle Installationen einer Runde werden gleichzeitig geprüft; die Units liest ein Aufruf `systemctl --user show -p Id,ActiveState -- <units>` mit 10 s Zeitlimit, ein nicht lesbarer oder unbekannter Wert ist `unknown`; Health `keine` heißt `{ zustand: unbekannt, grund: "keine Prüfung" }`; ein Grund nennt Status, Code oder Zeitlimit, nie eine Ausgabe oder Fehlermeldung eines Befehls; eine Installation `angelegt` fehlt in der Meldung; mit unlesbarem Gedächtnis schickt der Agent keine Meldung; Aufträge und Prüfung teilen eine Instanz des Gedächtnisses | eine leere Liste hieße für die Zentrale „keine Installationen“; eine ausgefallene Runde ist besser als doppelte Befehle im Container; eine geteilte Instanz sieht eine fertige Einrichtung sofort |
| Bewertung einer Installation | eine reine Funktion in `packages/planung` (`installationBewerten`) aus Health und Units: `rot`, wenn Health rot ist; sonst `gelb`, wenn eine Unit nicht `active` ist (`unknown` zählt als unbekannt); sonst `gruen`, wenn Health grün ist oder das Manifest `keine` hat; sonst `unbekannt`; jedes Ergebnis mit Grund (Unit und ActiveState, Status oder Fehler der Prüfung); ohne Meldung seit 90 s ist eine Installation `unbekannt` (Agent getrennt oder still) | eine beendete Nebeneinheit ist ein Warnzeichen, keine Störung; was nicht gemessen ist, ist nie grün |
| Zustand in der Zentrale | der aktuelle Zustand (Bewertung, Grund, seit, zuletzt gemeldet) steht an der Installation und wird als Messwert geschrieben, nicht ins Audit-Log; jeder Wechsel der Bewertung kommt als Zeile in `installation_verlauf` (je Betreiber, 90 Tage in der Aufbewahrung); eine Meldung für eine Installation eines anderen Servers wird verworfen und protokolliert | alle 30 s ein Audit-Eintrag je Installation wäre Rauschen; der Verlauf braucht nur die Wechsel |
| Störung | ist eine Installation 5 Minuten durchgehend `rot`, schreibt die Zentrale einmal ein Ereignis `stoerung` (Schwere `fehler`) über `schreiben`; wird sie danach `gruen`, ein Ereignis `stoerung_behoben` (Schwere `info`); geprüft bei jeder Meldung und in der Prüfung alle 30 s; `unbekannt` beendet keine Störung | plan.md, „Störung“; Z-703 und Z-903 benachrichtigen daraus |
| Bewertung im Einzelnen | eine Unit, die weder `active` noch `unknown` ist (auch `activating`, `reloading`), macht gelb, auch neben einer `unknown`; keine gemeldete Unit ist `unbekannt` („keine Units gemeldet“); eine gelbe Health-Prüfung bei aktiven Units ist `gelb`; ein Manifest, das sich nicht mehr lesen lässt, zählt als eines mit Prüfung; der Text des Agenten wird auf 500 Zeichen gekürzt; der Grund ist ein Code mit Werten (`health`, `unit`, `keine_units`, `nur_units`, `keine_meldung`, `noch_keine_meldung`), den die Oberfläche in ihrer Sprache sagt | ohne Units ist nichts gemessen; was die Prüfung als Warnung meldet, ist gemessen und nicht in Ordnung; ein Code lässt sich übersetzen, ein Satz der Zentrale nicht |
| Verlauf als Messwert | der Zustand an der Installation und die Zeilen in `installation_verlauf` schreibt nur `bewertungSetzen` (`modules/audit/messwerte.ts`) in einer Transaktion, ohne Audit-Eintrag; ein Wechsel ist ein Wechsel der Bewertung, nicht des Grundes; „seit“ bleibt, solange die Bewertung bleibt; die Aufbewahrung löscht den Verlauf über `schreiben` | ein flatternder Dienst würde sonst das dauerhafte Audit-Log füllen; Störungen, die etwas auslösen, gehen weiter über `schreiben` |
| Unbekannt nach 90 s | die Prüfung alle 30 s setzt eine Installation ohne Meldung seit 90 s auf `unbekannt` („keine Meldung seit 90 s“) mit dem Zeitpunkt, an dem die Meldung fällig war, als Wechsel im Verlauf; eine Meldung nach einer Stille setzt diesen Wechsel zuerst; die API rechnet dasselbe beim Lesen; eine Installation, die nie gemeldet hat, ist `unbekannt` ohne „seit“; anders als bei `server_still` zählt die Frist nicht erst ab dem Start der Zentrale | der Verlauf springt nicht über eine Stille; wie lange die Zentrale selbst weg war, weiß niemand, ein Zustand von damals ist unbekannt |
| Offene Störung | ob eine Störung offen ist, sagen die Ereignisse: das neueste `stoerung` oder `stoerung_behoben` mit Ziel `installation:<id>`; im selben Millisekunde zählt `stoerung_behoben` als später; rot zählt nur mit Meldungen (nach 90 s ohne ist die Installation unbekannt); der Text nennt Installation, Minuten und Grund auf Deutsch wie die übrigen Ereignisse | kein Zustand außerhalb der Ereignisse, wie bei `server_still`; ein Neustart wiederholt und vergisst keine Störung |
| Meldungen des Zustands | die Zentrale nimmt höchstens eine `zustand`-Nachricht alle 5 s je Verbindung an (wie Fortschritte); nennt sie eine Installation zweimal, gilt der letzte Eintrag; nur Installationen des Servers und Betreibers der Verbindung, die nicht `entfernt` sind; jede andere wird verworfen und als `state of an unknown installation dropped` mit Server und Installation geloggt | ein Agent, der zu oft meldet, soll die Tabelle nicht hämmern; ein Server spricht nur für seine Installationen |
| Zustand in der Oberfläche | die API liefert an jeder Installation `health` (`zustand`, `grund`, `seit`, `gemeldetAm`, `units` der letzten Meldung), die Seite dazu `verlauf` (die letzten 200 Wechsel, neueste zuerst); die Liste zeigt den Grund, wenn der Zustand nicht grün ist; die Seite zeigt „Units und Health“ und den Verlauf auch, solange die Installation eingerichtet wird, im Kopf aber bis `laeuft` den Zustand der Einrichtung; die Demodaten leiten Zustand und Verlauf aus der Health ihrer Installationen ab, ohne die 90-s-Regel | ein grüner Grund ist Rauschen in der Liste; die Demo soll nicht nach 90 s alles unbekannt zeigen |
| Formular der Einstellungen | eine reine Funktion in `packages/manifest` (`einstellungsFormular`) liefert aus Manifest, Ebene und Optionen die Felder (Name, Typ, Pflicht, Vorgabe, Beschreibung, geheim); `auto`-Werte und Vorlagen sind keine Felder; Oberfläche und Zentrale nutzen dieselbe Funktion, die Zentrale prüft damit jeden geschriebenen Wert; kein App-Name im Code | dieselbe Form für alle acht Apps; was die Oberfläche anbietet, nimmt die Zentrale auch an |
| Werte des Betreibers schreiben | `app_einstellungen` schreibt die Zentrale über `PUT /api/v1/apps/:app/einstellungen` (mit Grund, Inhaber und Technik) und im Dialog „App installieren“, der fehlende Pflichtwerte des Betreibers abfragt und in derselben Transaktion wie die Installation speichert; geprüft gegen das Schema des Manifests, mit dem geschrieben wird (im Dialog das hochgeladene, sonst das neueste der Installationen dieser App beim Betreiber); ein geheimer Wert kommt nie zurück, die API meldet nur „gesetzt“; ein leeres geheimes Feld behält den alten Wert | die erste Installation einer App braucht ihre Werte, bevor es eine Installation gibt; ein Geheimnis verlässt die Zentrale nur im Auftrag an den Agenten |
| Neu konfigurieren | `PUT /api/v1/installationen/:id/einstellungen` (mit Grund, Inhaber und Technik) ändert die Werte der Ebene `installation` und übernimmt die aktuellen Werte des Betreibers, rendert mit `einrichtungAuftragPruefen` gegen und legt den eingebauten Auftrag `installation_konfigurieren` an (dieselbe Form wie `installation_einrichten`, Optionen, Ports und erzeugte Werte bleiben); nur für eine laufende Installation, nie in einer Sperrzeit ihres Manifests (`sperrzeitAm`, 409), nie während ein anderer Auftrag der Installation offen ist; der Agent nimmt ihn nur für eine Installation an, die er fertig eingerichtet hat, schreibt Units, Slice, Dateien und Secrets neu (ein Secret mit `podman secret rm` und neu), `daemon-reload`, `restart` der Units, wartet, bis sie aktiv sind; scheitert ein Schritt, stellt er die alten Dateien und Secrets wieder her und startet neu; Volumes und Daten fasst er nie an; `schritte.einrichten` laufen nicht noch einmal | ein Neustart ist in einer Sperrzeit verboten wie ein Update; Rückkehr zum alten Stand statt Abbau, weil die Installation Daten hat |
| Alte Secrets beim Neukonfigurieren | der Agent liest die alten Werte vor dem Ändern selbst zurück: `podman secret ls --format {{.Name}}` und `podman secret inspect --showsecret` als Nutzer der Installation (Podman 4.5 und neuer), feste argv, die Ausgabe über eine Pipe nur in seinen Speicher (`lesen`, wie `systemctl show` der Prüfung, höchstens 64 KiB), nie in eine Datei, ein Log, ein Ergebnis oder einen Fehlertext (auch keine Meldung des JSON-Parsers); ein Name, der nicht wie die des Agenten aussieht (etwa mit `-` am Anfang), wird abgelehnt, bevor er in ein argv kommt; sind die Werte nicht lesbar, ändert er nichts | ein Gedächtnis mit Werten wäre eine zweite Klartextkopie jedes Geheimnisses auf dem Server und veraltete mit jedem Auftrag; der alte Auftrag liegt dem Agenten nicht vor (`auftraege.json` hält nur Ergebnisse); Podman hält die Werte ohnehin im Home des Nutzers, gelesen wird nur, was schon da ist |
| Was neu konfigurieren nicht ändert | der Agent vergleicht die gerenderten Units mit `pruefung.units` im Gedächtnis (eine Installation ohne, von vor Z-403, lehnt er ab) und verlangt, dass jede Datei, die er schreiben würde, schon da ist; Dateien, die der neue Stand nicht mehr hat, gibt es so nicht; gelesen werden sie mit `dateiLesen` (`O_NOFOLLOW`, nur reguläre Dateien), nachdem die Ordner wie beim Schreiben geprüft sind (kein Symlink) | der Agent kennt die alten Optionen nicht, aber die Units, die aus ihnen folgen; ein Symlink im Home darf root keine fremde Datei lesen und dann dem Nutzer übergeben lassen |
| Aktiv nach dem Neustart | nach `restart` wartet der Agent, bis die Units aktiv sind, und fragt dann zehnmal im Abstand von einer Sekunde, ob sie es bleiben; vor jedem `restart` steht `systemctl --user reset-failed` der Units, sein Code zählt nicht | die Units haben `Restart=always`: eine App, die beim Start abbricht, ist kurz aktiv und fällt erst nach dem Startlimit von systemd (5 in 10 s) aus; dieses Limit verweigert danach auch den Neustart des alten Stands, bis der Zähler zurückgesetzt ist |
| Wiederherstellen beim Neukonfigurieren | jeder Schritt mit eigenem Zeitlimit (60 s), nicht dem des Auftrags, und jeder läuft, auch wenn einer davor scheiterte: alte Dateien schreiben, `podman secret rm --ignore` aller alten und neuen Namen, alte Secrets anlegen, dann `daemon-reload`, `reset-failed`, `restart`, aktiv bleiben; der erste Fehler ist der Grund in „Wiederherstellung unvollständig: …“ | ein abgelaufenes Zeitlimit darf die Rückkehr nicht verhindern; so viel vom alten Stand wie möglich läuft wieder |
| Neu konfigurieren nach einem Neustart des Agenten | `installation_konfigurieren` ist nicht wiederholbar (`idempotent: false`): lief er beim Neustart, meldet der Agent ihn als „Agent neu gestartet“ gescheitert; die alten Secrets lagen nur im Speicher; ein neuer Auftrag mit den aktuellen Werten bringt die Installation wieder in Ordnung, weil er alle Secrets aus dem Auftrag neu anlegt | der Neustart der App käme sonst zu einer Zeit, die die Zentrale nicht geprüft hat (Sperrzeit) |
| Neu konfigurieren beim Zustellen | einen Auftrag `installation_konfigurieren`, den der Agent noch nicht bestätigt hat (`bereit`, `zugestellt`), sendet die Zentrale nicht, solange eine Sperrzeit seines Manifests gilt; er wartet auf die nächste Verbindung danach und bleibt so lange offen (`auftrag_offen`) | angenommen außerhalb der Sperrzeit, kann er bei einem Agenten, der erst in ihr wieder verbindet, sonst mitten in ihr die App neu starten |
| Fehlstart der Beispiel-App | die Beispiel-App bricht beim Start ab, wenn `BEISPIEL_TITEL` `beim-start-scheitern` ist, und zeigt den Titel unter `/` | der CI-Test des Neukonfigurierens braucht eine Einstellung, an der die App wie eine echte beim Start scheitert, nicht ein geändertes Manifest |
| Angefragte und gültige Werte | die angefragten Werte von „neu konfigurieren“ stehen in einer eigenen Tabelle `installation_konfigurationen` je Betreiber und Auftrag (nicht Geheimes als JSON, Geheimes verschlüsselt und an den Auftrag gebunden); die Spalten der Installation halten immer die gültigen Werte; beim Zustellen setzt die Zentrale `einrichtung` aus der Zeile des Auftrags zusammen; nach Erfolg übernimmt sie die Werte in derselben Transaktion, die das Ergebnis festhält (Geheimes neu an die Installation gebunden), jedes andere Ende (abgelehnt, gescheitert, Wiederherstellung unvollständig, „Agent neu gestartet“, abgebrochen) lässt die alten gültig; die Zeile geht mit jedem Ende | an den Auftrag gebunden bekommt ein zweites Zustellen dieselben Werte, und zwei Bedeutungen in einer Spalte der Installation gäbe es nie; gelöscht bleibt kein Geheimnis eines erledigten Auftrags liegen |
| Neuestes Manifest einer App | seit Z-501 das importierte Manifest der App mit der höchsten Version, die keine Vorabversion ist, sonst die höchste Vorabversion (SemVer, eine Vorabversion vor ihrer Version); es gilt für alle Betreiber, die Werte bleiben je Betreiber; bis Z-501 war es das der Installationen des Betreibers | eine Vorabversion gibt es nur für interne Installationen und soll nicht bestimmen, welche Werte jede Installation der App bekommt; die Installationen von vor Z-501 sind beim Start übernommen |
| Leere und fehlende Felder | ein Feld, das nicht mitkommt, bleibt, wie es war; ein leeres Textfeld nimmt den Wert weg (dann gilt die Vorgabe); ein leeres geheimes Feld behält den Wert, ein Geheimnis lässt sich über das Formular ändern, nicht löschen; ein Wert eines Namens, den das neueste Manifest nicht mehr kennt, bleibt in `app_einstellungen` | die Oberfläche zeigt kein Geheimnis und kann es nicht vorbelegen; eine ältere Installation kann einen alten Namen noch brauchen |
| Pflicht im Formular | Pflicht ist `pflicht` des Manifests; ein Pflichtfeld mit Vorgabe braucht keine Eingabe; der Dialog fragt ein Feld ohne Vorgabe nicht mehr als Pflicht ab | so rendert es auch `quadletsRendern` (`werteAufloesen`): nur ein Pflichtwert ohne Wert und Vorgabe fehlt |
| Werte des Betreibers im Dialog | der Dialog zeigt die Felder der Werte, die die Platzierung als `betreiberwert_fehlt` nennt, und schickt nur, was eingetragen ist, als `betreiberWerte`; die Zentrale prüft sie ohne Pflicht (`einstellungenPruefen` mit `pflicht: false`) gegen das hochgeladene Manifest, rechnet sie für Platzierung und Gegenrendern zu den gespeicherten und schreibt sie in der Transaktion der Installation; einen noch fehlenden Pflichtwert nennt die Platzierung wie zuvor; die Vorschau der Platzierung bekommt die Werte nicht | ein Geheimnis gehört nicht in eine Vorschau ohne Grund; derselbe Fehler (`passt_nicht` mit dem Namen), ob der Dialog Werte schickt oder nicht |
| Rechte der Einstellungen | die Werte des Betreibers lesen alle Rollen (`installationen:lesen`), Inhaber und Technik schreiben (`installationen:schreiben`); Support sieht sie in der Oberfläche nur lesend | sie dienen den Installationen und folgen deren Rollen |
| Aktionen einer Installation | Neustart und Log-Auszug sind eingebaute Aufträge (`installation_neustart`, `installation_log_auszug`, ohne Argumente, mit dem signierten Manifest), angeboten nur, wenn `aktionen.neustart` bzw. `aktionen.log_auszug` im Manifest `angeboten` ist (Vorgabe); „nur lesen“ ist der Befehl, den `aktionen.nur_lesen.befehl` nennt, als gewöhnlicher Auftrag (Z-305); Zentrale und Agent prüfen mit derselben reinen Funktion, ob eine Aktion angeboten ist, die Oberfläche zeigt nur angebotene; jede Aktion verlangt einen Grund (Audit-Log); Inhaber und Technik lösen sie aus, Support Log-Auszug und Neustart nur während eines Support-Zugangs (Z-802) | was das Manifest nicht anbietet, gibt es weder als Knopf noch auf dem Server |
| Neustart | der Agent: `systemctl --user restart` der Units als Nutzer der Installation, wartet, bis sie aktiv sind und 10 s bleiben; nur für eine fertig eingerichtete Installation; nie in einer Sperrzeit (die Zentrale lehnt beim Anlegen mit 409 ab und stellt einen noch nicht bestätigten Neustart in einer Sperrzeit nicht zu, wie bei „neu konfigurieren“); nicht bei einem offenen Auftrag der Installation; nicht wiederholbar nach einem Neustart des Agenten | ein Neustart in einer Sperrzeit ist verboten (CLAUDE.md, „Never“) |
| Log-Auszug | der Agent liest die letzten 500 Zeilen der Installation mit `journalctl _UID=<uid> -n 500 -o short-iso --no-pager` als root (der Nutzer-Journal-Zugriff hängt an der Speicherung), kürzt jede Zeile auf 2000 Zeichen und ersetzt vor dem Senden jeden Wert eines Geheimnisses durch `[geheim]`: die Werte der Podman-Secrets der Installation (gelesen wie beim Neukonfigurieren) und die Werte der Einstellungen vom Typ `geheim` und der Ebene `auto`, die als `Environment=` in ihren Units stehen (die Namen merkt er sich beim Einrichten, die Werte liest er aus den Units); längere Werte zuerst; er schickt die Zeilen als `log_auszug` mit der Auftrags-ID, das Ergebnis nennt nur die Zahl der Zeilen; die Zentrale speichert sie in `log_auszuege` (30 Tage) und zeigt sie nur Rollen mit Recht | ein Geheimnis darf nicht in die Zentrale gelangen; ein erzeugter Wert ist auch ohne `geheim` ein Schlüssel |
| Aktionen in der Zentrale | je Aktion eine Route unter der Installation (`POST …/neustart`, `…/nur-lesen`, `…/log-auszug`, jede mit Pflicht-`grund`, Audit-Aktion `installation.<aktion>`) und `GET …/log-auszuege/:auftragId`; ein eigenes Recht `installationen:log_auszug` für Inhaber und Technik (Support nur über einen Support-Zugang, Z-802), Neustart und „nur lesen“ verlangen `installationen:schreiben`; alle drei nur für eine laufende Installation; „nur lesen“ wartet wie der Neustart auf offene Aufträge, gilt aber in einer Sperrzeit (es startet nichts neu); der Log-Auszug läuft neben offenen Aufträgen und in einer Sperrzeit; nicht angeboten 422, Sperrzeit und offener Auftrag 409; die Seite einer Installation nennt unter `aktionen`, was das Manifest anbietet | Support liest Logs, ändert aber nichts; der Agent kennt den Nutzer einer Installation erst nach dem Einrichten; wer bei einer hängenden Installation die Logs braucht, soll nicht auf deren Auftrag warten |
| Log-Auszug annehmen | die Zentrale speichert `log_auszug` nur für einen Auftrag `installation_log_auszug` des meldenden Servers und Betreibers, einmal je Auftrag (`auszug_id` = Auftrags-ID), unabhängig vom Zustand des Auftrags (die Reihenfolge von Zeilen und Ergebnis legt der Agent fest); jede Zeile auf 2000 Zeichen gekürzt; anderes verwirft sie mit einem Log-Eintrag ohne die Zeilen; das Audit-Log vermerkt den Auszug mit `inhalt` als „[ausgelassen]“ | ein Agent kann so keinen fremden oder zweiten Auszug unterschieben; das Audit-Log bleibt dauerhaft, die Zeilen enthalten Daten der Kunden und gehen nach 30 Tagen |

| DCO | Commits des Loops tragen das `Signed-off-by` des Maintainers (Git-Identität der Loop-Sessions), Claude steht als `Co-Authored-By` darunter | das DCO ist die Erklärung einer Person |
| Beiträge | DCO (Signed-off-by), kein CLA | Open Source ohne Sonderrechte |
| Kunden und Verträge | ein Kunde mit einer Ansprechperson (Name, E-Mail, Telefon) und Notiz; in Stufe 1 genau ein Vertrag je Kunde, mit ihm angelegt (eindeutiger Index auf Betreiber und Kunde, Fremdschlüssel auf den Kunden); SLA in der Tabelle `basis`, `plus`, `ruhe`, die API nimmt bis Z-505 nur `basis`; die Kündigung ist das Vertragsende (`vertraege.ende`, nullable), gesetzt und zurückgenommen über eigene Routen; Vertragsbeginn und -ende sind der Beginn ihres Tages in `Europe/Berlin` als UTC-Millisekunden (ein anderer Zeitpunkt wird mit `400` abgelehnt), das Ende nie vor dem Beginn; Ändern ersetzt die Angaben (`PUT`) und schreibt nur geänderte Felder ins Audit-Log, ohne Änderung keinen Eintrag; jede schreibende Route verlangt `grund` | mehrere Verträge je Kunde braucht Stufe 1 nicht, ein Index lässt sich später ohne Datenumbau lösen; ein Tag ist kein Zeitpunkt, der Beginn in Berlin hält die Anzeige TT.MM.JJJJ in jeder Zeitzone gleich; ein Eintrag je unverändertem Feld wäre Rauschen |
| Rollen für Kunden | alle Rollen sehen Kunden und Verträge; Inhaber und Technik legen an, ändern und kündigen; Support nur lesen | Technik richtet Installationen ein, die von einem Kunden ausgehen; Support braucht den Kunden für Support-Zugänge (Z-802), ändert aber keine Verträge |
| Kundenseiten vor Z-406 | Kundenliste und Kundenseite lesen und schreiben über eine eigene Quelle (`apps/web/src/daten/kunden.ts`): angemeldet die API, in `dev:demo` die Demodaten im Speicher; Installationen, Ereignisse und Support-Zugänge eines Kunden kommen bis Z-406 weiter aus den Demodaten, ein Kunde der Zentrale hat also noch keine; Solid 2 async (`createMemo` unter `<Loading>`, `refresh` nach dem Schreiben), ohne TanStack Query | Z-801 bringt Kunden, nicht Installationen; eine Quelle je Bereich lässt die übrigen Seiten bei den Demodaten, bis ihr Punkt sie umstellt; für zwei Seiten mit wenigen Anfragen braucht es keinen Cache |
| Installationsseiten vor Z-406 | Liste und Seite einer Installation und der Dialog „App installieren“ lesen und schreiben über `apps/web/src/daten/installationen.ts` (angemeldet die API, in `dev:demo` die Demodaten im Speicher, die wie die API antworten); der Zustand kommt seit Z-403 von der Zentrale; Backups, Daten, Einstellungen aus dem Manifest und Ereignisse kommen bis Z-406 nach der ID aus den Demodaten, eine Installation der Zentrale zeigt dort „–“; Übersicht, Server- und Kundenseiten zeigen bis Z-406 weiter die Installationen der Demodaten, ein Verweis von dort kann auf „Nicht gefunden“ führen; der Dialog liest das hochgeladene Manifest im Browser mit `manifestPruefen` (`packages/manifest`, nachgeladen, nicht im Bundle jeder Seite) und fragt die Platzierung bei jeder Änderung neu, nur deren Feld wartet (`<Loading on>`); Knöpfe zum Anlegen und Entfernen zeigt die Oberfläche nur Inhaber und Technik (Rolle aus `GET /api/v1/ich`); in den E2E-Tests tritt ein Stellvertreter des Agenten mit dem Einmal-Token bei und meldet Fakten, die Zentrale prüft das Manifest mit dem öffentlichen Test-Schlüssel als `minisign.pub` | Z-402 bringt Installationen, nicht Health und Backups; dieselbe Prüffunktion im Browser zeigt Optionen und Einstellungen, bevor die Zentrale gefragt wird, und kein App-Name steht im Code; die Platzierung im Feld zu halten, lässt die übrigen Eingaben nicht auf die Zentrale warten; ohne verbundenen Agenten mit Fakten passt keine App, und ein echter Agent in Playwright braucht Podman und systemd, die nur die Agent-Tests der CI haben |
| Oberfläche vor der API | die Seiten lesen über eine Datenschicht (`apps/web/src/daten/`), die bis Z-406 die Demodaten aus `apps/web/src/demo/` liefert: ein Betreiber, Stufe 1 (nur SLA Basis, Wellen „intern“ und „alle“, installiert sind Haben, Belegt, Schreibzeug, Fixpunkt), die Seite „Apps“ zeigt alle acht; schreibende Aktionen (Knöpfe, Dialoge mit Grund) kommen erst mit ihrem Punkt, Einstellungen sind bis dahin nur lesbar | ein Knopf ohne Wirkung täuscht; die Demodaten sind zugleich Vorlage für die API und Grundlage für E2E und Screenshots |
| Echte Apps (Z-1003) | die CI richtet Schreibzeug und Haben aus `manifeste/` mit ihren Images von GHCR ein (öffentlich, ohne Anmeldung abrufbar), sichert, stellt wieder her und aktualisiert sie: Schreibzeug 0.1.25 → 0.1.26 auf dem Weg der Welle (Plan der Zentrale mit `planInstallation` und `updatePlan`, Kunde intern, Wartungsfenster ganztägig), Haben 0.12.0-rc.1 → 0.12.0 von Hand; GHCR hat von Haben nur diese beiden Versionen, das Paar ist also eine Vorabversion und ihre Version (Kunde intern). Haben nennt seit 0.12.0 `/api/health` (Quelle in `manifeste/haben/*/QUELLEN.md`), das Manifest behält deshalb `health: http`; für das Update ohne Health ersetzt der Test die Zeile durch `health: keine` und signiert neu mit dem Testschlüssel. `manifeste/` hält dafür zwei Versionen von Schreibzeug und Haben; ihre Golden Files heißen `<app>@<version>`, die Tabelle der Apps gilt für jede Version. Der Grund eines Updates von Hand bleibt in der Zentrale (`modules/updates/anlegen.test.ts`), der Auftrag an den Agenten ist derselbe | ein Update gilt erst, wenn es mit den echten Images der Apps läuft; ein Wert im Manifest braucht eine Quelle, eine Testvariante steht sichtbar im Test |

## Datenmodell

Betreiber → Kunde → Vertrag (SLA) → Installation (App, Version, Server, Port, Adresse, Optionen,
Einstellungen) → Server (Art, Wartungsfenster, Fakten, Zertifikat des Agenten). Dazu Manifest (App,
Version, Inhalt, Signatur), Auftrag (Art, Ziel, Zustand, wartet auf, Ergebnis), Ereignis, Backup
(Repository je Installation, Snapshot, Prüf-Restore), Prüfung von außen, Einstellung (Ebene, Wert,
verschlüsselt), DNS-Eintrag, API-Token, Webhook, Audit-Log. Partner sind Betreiber.

## Sicherheit

- Oberfläche nur über WireGuard; `agent.` mit mTLS, `api.` mit Token; Rate-Limits an Anmeldung,
  Token-Tausch und API.
- Jedes Konto mit Passkey oder TOTP; jede schreibende Aktion im Audit-Log mit Grund.
- Manifeste und Agent-Binaries signiert, Images per Digest; der Signierschlüssel liegt offline beim
  Inhaber. Eine übernommene Zentrale kann Server anhalten, aber keinen fremden Code ausführen.
- Ein gestohlenes Agent-Zertifikat fälscht höchstens Meldungen dieses Servers.
- Server bekommen keinen DNS-Token und keinen S3-Schlüssel eines anderen Kunden.
- Notzugang per SSH nur über WireGuard, jede Anmeldung als Ereignis.
- `docs/sicherheit.md` führt Bedrohungen und die technischen und organisatorischen Maßnahmen nach
  Art. 32 DSGVO als Anlage zum Auftragsverarbeitungsvertrag.

## Bauplan im Agenten-Loop

Ein Agent arbeitet die Bauliste Punkt für Punkt ab, bis jedes Häkchen gesetzt und jede Prüfung grün
ist. Er wartet nie auf einen Menschen.

1. **Spezifikation zuerst**: das Manifest-Schema und die Kriterien je Punkt. Ohne Kriterium kein Code.
2. **Ein Durchlauf, ein Punkt**: reservieren (Draft-Pull-Request), Tests zuerst, umsetzen, Doku
   nachziehen, `bun run check` grün, unabhängiges Review (`tdd-review`), CI grün, selbst mergen,
   abhaken.
3. **Entscheiden statt fragen**: offene Fragen nach „Entscheidungen“; neue mit Grund dort eintragen.
4. **Nicht hängen bleiben**: dreimal gescheitert heißt zurückgestellt.
5. **Echt testen**: der Agent läuft in der CI gegen Podman mit systemd, mit einer Beispiel-App aus
   diesem Repo; eine echte App (Schreibzeug) in der Härtung.

Zwei Stufen, damit die ersten Kunden früh laufen und Stufe 2 aus echtem Betrieb lernt:

- **Stufe 1 – eigener Betrieb** (41 Punkte): 1 Fundament · 2 Manifest und Platzierung · 3 Agent ·
  4 Installationen mit DNS · 5 Updates (Wellen „intern“ und „alle“) · 6 Backups und Kündigung ·
  7 Server-Pflege, Prüfung von außen, Kunden, Support-Zugang, Leistungen, Härtung, Release 1.0.
  Betrieben werden Haben, Belegt, Schreibzeug und Fixpunkt auf unseren Servern, ein Betreiber.
- **Stufe 2 – wachsen** (10 Punkte), erst nach Freigabe durch einen Menschen: 8 weitere Betreiber
  (Partner) · 9 Kontext mit eigenen Domains, Mail und Single Sign-on · 10 API für das Portal ·
  11 Wellen nach SLA mit Ankündigung · 12 Umzug und Ausfall automatisiert.

Das Schema trägt Stufe 2 schon (`betreiber_id`, SLA, `braucht`/`bietet`, `dns`), damit später keine
Migration alter Daten nötig ist; gebaut wird es erst mit seinem Punkt.

## Offene Fragen

- Name und Domain der Steuerzentrale (Arbeitstitel); davon hängen `agent.<domain>` und
  `api.<domain>` ab.
- Bezahlter Archivbetrieb für gekündigte Kunden mit GoBD-Daten: ja oder nein, zu welchem Preis?
- Ein Kontext für mehrere Kunden (Stalwart kann mehrere Domains): spart Server, bricht aber „eine
  Installation, ein Kunde“; Entscheidung nach den ersten Kunden.
